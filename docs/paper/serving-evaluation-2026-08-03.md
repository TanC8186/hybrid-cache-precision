## 1. Experiment Setup

**Platform.** All serving experiments run on a single RTX 5090 (32 GB HBM, Blackwell sm_120)
in the pinned Docker environment of `configs/env/remote_5090.yaml`. We use **Qwen3.5-2B**, a
hybrid linear-attention transformer with 18 Gated DeltaNet (GDN) layers and 6 standard GQA
attention layers at indices $\{3,7,11,15,19,23\}$, each attention layer with 2 KV heads of
head_dim 256. The serving stack is a vLLM **0.26.1rc1** fork (`vendor/vllm`) carrying two
patches: per-layer `kv_cache_dtype` override and a CLI-help fix (diff archived in
`vendor/vllm-patches/`). Servers run as OpenAI-compatible endpoints (`vllm serve`); load is
generated by `vllm bench serve`.

**Configurations compared.** (a) **fp16 baseline**: `kv_cache_dtype=auto` (bf16). (b) **uniform
4-bit (ours)**: `kv_cache_dtype=int4_per_token_head` — every GQA attention layer stores K/V as
int4-per-token-per-head with a per-token scale. We also characterize a **sensitivity-guided
per-layer variant** (layer 23 kept at full precision, the remaining GQA layers int4), motivated
by the layer-sensitivity analysis of §6. As §8 shows, this variant currently *loses* capacity in
the vLLM V1 KV manager (mixed-dtype page unification), so it is reported as a limitation rather
than the serving mainline.

**Protocol.** Both servers use `gpu_memory_utilization=0.85`, `max_model_len=4096`,
**CUDA-graph mode** (`enforce_eager=False`), and `enable_chunked_prefill=True`. The benchmark
(`vllm bench serve --dataset-name random`) issues **400 requests per rate point** with fixed
**input_len=1024 / output_len=128** (confirmed in server logs), Poisson arrivals
(`burstiness=1`), `--max-concurrency 512`, and offered rates
$R \in \{1,4,8,12,16,20,30,40,50,75\}$ req/s. All points complete with **zero failed
requests**. `num_warmups=0`; server-side `disable_log_stats=False` so `RequestOutput.metrics`
(TTFT/TPOT) are recorded.

**SLO.** Following `configs/bench/throughput.yaml`, an allocation is SLO-compliant when
**TTFT p99 < 2000 ms and TPOT p99 < 200 ms**.

## 2. E1 — KV Cache Capacity

Under a fixed GPU memory budget, uniform 4-bit grows the KV cache from 1,203,106 to
2,701,721 tokens and the engine's maximum concurrency from 293.7 to 659.6 sequences
(Table 1; server startup logs archived in commit `525020f`). The end-to-end capacity ratio is

$$\text{capacity} = \frac{2,\!701,\!721}{1,\!203,\!106} = 2.2456\times .$$

| allocation | KV cache (tokens) | max concurrency | KV cache memory |
|---|---|---|---|
| fp16 | 1,203,106 | 293.7 | 20.12 GiB |
| int4 uniform (ours) | 2,701,721 | 659.6 | 20.08 GiB |
| **ratio** | **2.2456x** | **2.245x** | — |

**Table 1.** E1 capacity from server startup logs (`GPU KV cache size` / `Maximum
concurrency`), Qwen3.5-2B, gpu_util=0.85, max-len 4096, CUDA-graph mode.

**Dual caliber.** The *mechanism-level* compression of the attention KV cache alone is
**3.88x**: each GQA layer stores $2 \times 256 \times 2\,\text{B} \times 2\,(K{+}V) =
2048\,\text{B}$ per token per layer in fp16, and ${\approx}528\,\text{B}$ under
int4-per-token-per-head (including the per-token scale), so $2048/528 = 3.878x$. This matches
the offline slot counts (7,434,528 int4 vs 1,917,056 fp16, §5/§6). The *system-level* ratio is
**2.2456x** — i.e. **only ~58% of the mechanism-level gain survives** end to end.

**Why: non-quantizable Gated DeltaNet state.** The GDN recurrent state is stored per sequence
and is *not* quantized by the KV scheme. From `MambaStateShapeCalculator
.gated_delta_net_state_shape` (`vendor/vllm/.../mamba/mamba_utils.py`):

- temporal state `(num_v_heads=16, head_v_dim=128, head_k_dim=128)` = 262,144 elements, fp32
  → 1,048,576 B;
- conv state `(conv_dim=6144, conv_kernel-1=3)` = 18,432 elements, bf16 → 36,864 B;
- per layer **1,085,440 B**; × 18 layers = 19,537,920 B ≈ **18.63 MiB per request**.

GDN state grows **linearly with the number of concurrent sequences** (independent of context
length) and is drawn from the *same* KV-cache memory pool as the attention blocks. At the int4
server's maximum concurrency (659.6 sequences), aggregate GDN state ≈ 12.0 GiB ≈ **60% of the
20.08 GiB KV-cache budget** **[VERIFY — provenance estimate, see §7]**; at the 400 requests
observed in flight at the highest offered rate it is ≈ 36%. Because this fixed per-sequence cost
is identical for both allocations, it dilutes the 3.88x attention-KV gain to 2.2456x end to end.

**Capacity scales with context (2026-08-03).** At `max_model_len=16384` the ratio grows to
**3.155x** (int4 4,910,731 vs fp16 1,556,961 tokens; both server logs first-hand). Mechanism
(server log `interface.py:911`): vLLM forces the attention `block_size` so that the attention
page size ≥ the mamba page size (1,085,440 B) → fp16 block 544 tokens / int4 block 2064 tokens
(each ≈1.09 MB page). At long context the concurrency ceiling drops (int4 659.6 → 299.7), so the
fixed per-sequence GDN state consumes a smaller fraction of the budget, dilution weakens, and the
capacity ratio moves back toward the mechanism-level 3.88x. On **Qwen3.5-9B** (24 linear +
8 full-attention layers), uniform int4 gives 328,499 vs fp16 150,062 tokens = **2.19x** @4096
(server logs `serve9b_int4.log` / `serve9b_bf16.log`).

**Structural implication.** In a hybrid architecture, quantizing only the (small number of) GQA
attention layers has a capacity ceiling set by the linear-attention per-request state. Further
capacity gains require either compressing the GDN state itself or an honest end-to-end caliber.
**We report both calibers** (mechanism 3.88x, system 2.2456x) throughout.

## 4. E3 — SLO-Constrained Capacity (protocol-v2, VERIFIED)

The canonical SLO evidence is the **protocol-v2 steady-state matrix**: fixed 60 s Poisson arrival
window, 120-request warmup, `goodput / offered ≥ 0.95` sustainability, seeds {7, 42, 2026},
TTFT thresholds {250, 500, 1000, 2000, 3000} ms, TPOT 200 ms. The formal matrix completed
72/72 samples and 160,200/160,200 requests with zero failures; an independent reproduction
matched 80/80 cell means within 10% (max 4.993%) and 60/60 boundaries exactly
(`results/verified/2026-08-04/e3/`, verdict REPRODUCIBLE).

**Sustainable offered-rate boundary (mean over 3 seeds; all seeds must satisfy the criterion):**

| Workload | TTFT threshold | FP16 boundary | INT4 boundary | Relative change |
|---|---:|---:|---:|---:|
| Random | 250 ms | 35.00 | 35.00 | +0.0% |
| Random | 500 ms | 35.00 | 36.67 | +4.8% |
| Random | 1000 ms | 35.00 | 40.00 | +14.3% |
| Random | 2000 ms | 35.00 | 40.00 | +14.3% |
| Random | 3000 ms | 35.00 | 40.00 | +14.3% |
| ShareGPT | 250–3000 ms | 28.33 | 23.33 | **−17.6%** |

**Table 3.** Protocol-v2 sustainable SLO boundaries (VERIFIED). Rates are offered req/s; a
boundary is sustainable when all three seeds achieve goodput/offered ≥ 0.95 at the given TTFT
threshold with TPOT ≤ 200 ms. Confidence is CAUTION: n = 3 seeds, 5 req/s rate grid, and wide
ShareGPT intervals.

**Result.** The SLO effect of uniform int4 is **workload- and threshold-dependent**. On synthetic
Random traffic the boundary gain is 0% at the strictest 250 ms threshold, +4.8% at 500 ms, and
+14.3% at 1000–3000 ms. On the real ShareGPT trace the boundary is **lower** for int4 (−17.6%),
reversing the synthetic direction. Therefore no workload-general claim is made; Random and
ShareGPT are reported separately, and the earlier "+25%" single-run reading is withdrawn
(it reflected an overloaded transient, not a sustainable boundary).

**TPOT is not binding anywhere.** Across the protocol-v2 matrix TPOT p99 stays far below the
200 ms bound; the SLO is TTFT-bound in both allocations.

**Historical note.** The original single-run E2/E3 matrix (`bench_lat`, 10 rates, 400
requests/point, `num_warmups=0`) is retained in the archive as background/exploratory data. It
produced the withdrawn +25% reading and is not used for any paper claim.

## 5. TPOT Per-Token Cost

Figure 3 (`fig3_tpot.png`) plots TPOT p50/p99 vs. goodput for both allocations (4 lines).

**Real per-step cost.** The honest cost of uniform 4-bit KV quantization is a per-token latency
increase from per-layer RHT dequantization and the Triton attention kernel. Offline 3-seed
measurements (@4096, warmup protocol, `enforce_eager=True` — note this differs from the
CUDA-graph serving protocol) give **TPOT p50 +8.0%** for uniform int4 (33.8 vs 31.3 ms, warmup
120, 3-seed) and throughput **−5.5%** (2017 vs 2135 out-tok/s). Across the warmup protocols we
tested (5 vs 120) the uniform-int4 cost spans **−6~8% throughput and +8~10% TPOT p50**
(`bench_uniform_int4_4096_*` and `bench_uniform_int4_warm_4096_*`). At 8192 context (single
seed) the throughput cost shrinks to −3.1%. These directionally match the low-load latency gap
in §3 and the ShareGPT trace (§6/§8).

**p99 tail is not an inherent int4 cost.** We initially observed a large TPOT p99 tail for int4
in a non-warmed serving run (p50 31→44 ms, **p99 894 ms**, ratio ≈ 20x). Root-cause analysis
(`jit_monitor` logs + backend selection) shows the spike is a **serving-time Triton JIT cold
compile** of the int4 attention kernels (`_attn_packed`, `reduce_segments`): int4 forces the
`TRITON_ATTN` backend (fp16 uses the precompiled `FLASH_ATTN`), and the engine profile/warmup
paths do not pre-compile the 2D-decode specialization (decodes with batch > 64), which is first
compiled inside the measured window. Re-running with `--warmup-n 120` (warmup concurrency
120 > 64, forcing all decode specializations) **eliminates the spike**: uniform-int4 TPOT p99
returns to ≈ 144.7 ms (3-seed mean), comparable to fp16 (145.5 ms). In the CUDA-graph serving
matrix (§4) TPOT p99 stays ≤ 49.3 ms throughout. **We report warmup-clean TPOT and disclose the
warmup gap in §7.**

## 6. Quality under a Byte Budget

The serving gains rest on int4 quality. Table 4 reports the **canonical 3-seed** Wikitext-2 PPL
(seeds {7, 42, 2026}; 5 × 2048-token sequences per seed; chunk 128; greedy, deterministic) across
bit-widths and eviction retention. Paired differences are computed per seed against the FP16
run of the same seed; 95% CIs are t-based over n = 3 seeds. The canonical source is
`results/ablations/byte_budget_3seed.csv` (final harness). An earlier 3-sequence/seed file and a
single-seed byte-budget file are retired from headline use (the single-seed file remains only as
the anchor protocol for the deterministic sensitivity tables below).

| bits | keep (tokens) | KV bytes | PPL (mean ± SD) | vs FP16: paired Δ [95% CI] |
|---|---|---|---|---|
| 2 | 2048 (full) | 3,366,816 | 19.00 ± 3.19 | +7.52 [+3.50, +11.54] |
| 3 | 2048 (full) | 4,852,176 | 13.53 ± 1.87 | +2.05 [+1.15, +2.95] |
| **4** | **2048 (full)** | 6,436,560 | **11.67 ± 1.61** | **+0.19 [+0.09, +0.30]** |
| 8 | 2048 (full) | 12,774,096 | 11.48 ± 1.57 | −0.00 [−0.01, +0.01] |
| FP16 | — | 25,350,144 | 11.48 ± 1.57 | baseline |
| 4 | 1024 | 3,194,880 | 11.85 ± 1.66 | vs 2-bit full: −7.15 [−10.97, −3.34] |
| 4 | 1536 | 4,792,320 | 11.71 ± 1.62 | vs 3-bit full: −1.82 [−2.65, −0.99] |

**Table 4.** Canonical 3-seed quality (Wikitext-2 PPL), `byte_budget_3seed.csv`. Byte budgets
use the packed per-token theoretical bytes (as in §6.1 of the design note); equal-byte pairs are
not byte-exact (tolerance ≤ 5.4% at ≈3.2 MB, 1.3% at ≈4.8 MB), and the ordering is robust within
this tolerance in every seed.

**Findings.**

1. **8-bit is lossless** (paired Δ ≈ 0, CI includes 0); **4-bit is near-lossless but measurably
   nonzero**: +0.19 PPL, **+1.7%** [95% CI 0.8%–2.6%] vs. FP16. The tension zone is below 4 bits:
   3-bit +17.8% [10.0%–25.7%], 2-bit +65.5% [30.4%–100.5%]. With n = 3 seeds the CIs are wide;
   "near-lossless" is reported with this uncertainty, not as a statistical equivalence claim.
2. **Equal-byte-budget ordering: high precision + eviction beats low precision + full
   retention.** At ≈3.2 MB, 4-bit keep-1024 (11.85 ± 1.66) beats 2-bit full retention
   (19.00 ± 3.19), paired Δ −7.15 [−10.97, −3.34]; at ≈4.8 MB, 4-bit keep-1536 (11.71 ± 1.62)
   beats 3-bit full retention (13.53 ± 1.87), paired Δ −1.82 [−2.65, −0.99]. Under a fixed byte
   budget, *evict tokens before dropping below 4-bit*.
3. **Layer heterogeneity (deterministic single-protocol, 3-seed replication pending).** The
   sensitivity sweep (results/ablations/layer_sensitivity.csv) anchors on the deterministic
   single-seed protocol (all-8-bit 13.63, all-2-bit 21.07): forcing layer 23 to 2-bit costs
   +28.7% of the 2-bit sensitivity range (PPL 15.76 vs 13.63) — the most sensitive layer — while
   layer 3 is essentially free (−5.9%). This motivates sensitivity-guided per-layer protection;
   the 3-seed replication of these anchors is pending (Remaining Gaps).
4. **Sensitivity-guided allocation beats uniform at equal bytes (deterministic
   single-protocol).** `sens_guided` {3:2bit, middle 3bit, 23:4bit} → PPL 14.63 @ 4.87 MB vs
   uniform 3-bit 15.87 @ 4.85 MB; `only_layer3_2bit` {3:2bit, others 4bit} → PPL 13.39 @ 5.92 MB
   — better quality *and* fewer bytes than uniform 4-bit (13.86 @ 6.44 MB) on the same
   deterministic protocol. This is the transformers-path evidence that motivates making per-layer
   protection capacity-neutral in the serving system (§8).

**A2 quality closure (ANALYZED, 2026-08-06).** We compared fp16, uniform int4, and packed
per-layer (L23 bf16) on (i) Wikitext-2 PPL under the same 3-seed canonical protocol as Table 4
(`results/quality/r4-ppl/`) and (ii) a seeded NIAH retrieval matrix (3 depths × 2 lengths
{2048, 4096} × 3 seeds × 3 needles, vLLM offline greedy, `results/quality/r4-niah/`, 54/54
samples, zero failures):

| Allocation | PPL (mean ± SD, 3 seeds) | NIAH accuracy (18 cells) |
|---|---:|---:|
| fp16 | 11.4827 ± 1.5732 | 0.9074 |
| uniform int4 | 11.6811 ± 1.5861 | 0.9074 |
| packed per-layer | 11.5985 ± 1.5534 | **0.9259** |

**Table 4b.** A2 quality closure. Paired results (95% t-CI, df=2): packed vs. uniform int4
PPL Δ = **−0.083 [−0.177, +0.012]** (−0.71%); NIAH Δ = **+0.019 [−0.051, +0.088]**. The capacity
recovery of packed per-layer (0.833× of uniform int4) therefore does **not** come at a quality
cost on these metrics; point estimates favor packed (L23 protection). Status: ANALYZED —

## 7. Discussion / Honesty

We state the caveats that qualify every claim above.

- **Mainline re-basing (bug disclosure).** All "per-layer" serving numbers previously reported
  were in fact **uniform int4**: `vendor/vllm/.../engine/arg_utils.py` dropped
  `kv_cache_dtype_per_layer` when constructing `CacheConfig`, so the per-layer override never
  took effect (fixed, `vendor/vllm-patches/per-layer-kv-dtype.diff`; server site-packages
  synchronized and re-verified). The uniform-int4 numbers in §2–§5 are therefore real, and the
  per-layer claims in the original draft are withdrawn in favor of §8's limitation framing.
- **Model scale.** All serving results use **Qwen3.5-2B**. The capacity claims (2.245x @4K,
  3.155x @16K) and the protocol-v2 E3 boundaries are validated on 2B; Qwen3.5-9B has capacity
  probes only (2.19x @4096, 3.167x @16384) and a single-run E2 saturation check. A 9B E3 matrix
  has not yet been run and must not be claimed.
- **Workload.** The E3 protocol-v2 matrix combines a synthetic `random` workload (1024-token
  inputs / 128-token outputs) with the real ShareGPT trace (`ignore_eos` paired completion
  lengths, 300 s window in the A2 serving protocol). The two workloads **reverse direction**
  (Random +14.3% at loose thresholds vs ShareGPT −17.6%), so all claims are workload-specific.
- **Statistics.** The E3 boundaries are 3-seed mean values with the all-seeds-satisfy
  sustainability criterion (VERIFIED, n = 3, CAUTION). The historical E2 matrix remains a
  **single run per (allocation, rate)** and is retained only as background; its saturation
  goodput (≈+5%) is directionally consistent with the 3-seed E2 note
  (`docs/notes/serving-3seed-9b-2026-08-03.md`) but is not used for headline claims.
- **Protocol.** The protocol-v2 E3 matrix fixes a 60 s arrival window, 120-request warmup, and
  explicit failure accounting (`completed + failed = expected`; failures stay in the offered
  denominator as SLO misses). The historical matrix used `num_warmups=0`; the offline matrix
  mixes `warmup_n=5` and `warmup_n=120` across allocations. §5 shows the warmup protocol can
  dominate p99 conclusions.
- **Capacity provenance.** Server startup logs (KV cache size, max concurrency) are archived in
  commit `525020f` + later commits (`2f7ded9`). The **GDN ≈ 60%-of-budget** figure is derived
  from the archived max concurrency and the code-derived per-sequence state size; it is an
  estimate and should be re-verified against the exact logged KV-memory split **[VERIFY]**.
- **Both capacity calibers are reported** (mechanism 3.88x, system 2.2456x) to avoid
  overselling the compression ratio.
- **Per-layer limitation.** See §8 for the quantified capacity regression of mixed-dtype KV
  allocation under the current vLLM V1 KV manager.

## 8. Legacy Limitation and Its Fix: Packed Per-Layer Page Groups (A2)

Sensitivity-guided per-layer allocation (protecting the most sensitive attention layer in full
precision) is attractive at the quality level (§6). In the **legacy** vLLM V1 KV manager it is not
deployable without a catastrophic capacity penalty — a system-level finding that motivated our
packed per-layer page-group mechanism (mainline §4). We first quantify the legacy regression, then
report the fix.

**Quantified regression.** With the per-layer wiring fixed, protecting layer 23 (kept at `auto`
= bf16, the correct protection dtype for a bf16 model; fp16 protection crashes flash-attn due to
query/key dtype mismatch) while quantizing all other GQA layers to int4 gives:

| model | true per-layer | uniform int4 | fp16 baseline | per-layer / uniform |
|---|---|---|---|---|
| Qwen3.5-2B @4096 | 696,456 tokens (170.0x conc) | 2,701,721 (659.6x) | 1,203,106 (293.7x) | **×0.258** |

**Table 5.** Server-log KV cache size (`GPU KV cache size`, = max_concurrency × max_len), from
`serve2b_pl.log` / `serve9b_int4_v2.log` (true per-layer) vs `server_pl.log` / `serve9b_int4.log`
(uniform) vs `server_fp16.log` / `serve9b_bf16.log` (fp16). Capacity comparisons must use the
server-log size: under per-layer, the bench JSON `kv_cache_total_slots` is distorted because it
still counts blocks at the int4 `block_size` (2064) rather than the unified bf16 page.

Per-layer capacity is **×0.258 of uniform int4**, i.e. a **~3.87x loss**, and the regression is
**identical across 2B and 9B** (0.2578 vs 0.2581), indicating a deterministic mechanism rather
than model-specific noise. The per-layer cache is even **below the fp16 baseline**: 696,456 <
1,203,106 (2B) and 84,787 < 150,062 (9B) — roughly 56–58% of fp16. Max concurrency falls to
170.0 (2B) / 20.7 (9B), below fp16's 293.7 / 36.6.

**Mechanism: uniform page-size unification.** vLLM V1 requires a single uniform page size per KV
pool (`kv_cache_utils.get_uniform_page_size` assertion). Mixing dtypes triggers
`unify_kv_cache_spec_page_size`, which unifies every layer to the **largest** page: a bf16 layer
needs 4× the bytes of an int4 layer, so the unified page is 4× the int4 page and the int4 layers'
`block_size` inflates from 2064 to 8256. Consequences: (1) all attention layers are accounted at
the bf16 page size (physical memory 4×), and (2) layers with different `block_size` cannot share
a KV group, so the number of groups explodes and per-request block overhead multiplies — the
observed collapse in `max_concurrency`.

**True per-layer also costs throughput/latency.** 3-seed offline bench (warmup-120, eager,
gpu_util=0.90) of the true per-layer config vs the uniform-int4 config
(`bench_default_alloc_perlayer_4096_{7,42,2026}.json` vs `bench_default_alloc_4096_{7,42,2026}.json`):
throughput **−8.2%** (1834.8 vs 1999.6 out-tok/s), TPOT p50 **+13.8%** (38.7 vs 34.0 ms — even
worse than uniform int4's +8~10% vs fp16). Interestingly, TPOT p99 *improves* (47–92 vs 88–159
ms) because the bf16-protected layer bypasses the int4 Triton-attention JIT (§5). The capacity
regression dominates and makes the config unattractive end to end.

**Fix: packed per-layer page groups (A2).** The loss is not inherent to mixed-dtype KV; it is an
artifact of the uniform-page configuration layer. We implement `--enable-per-layer-page-groups`
(mainline §4): the six full-attention layers are merged into one mixed-precision
`UniformTypeKVCacheSpecs` group (five int4 + one bf16) that shares a block table, while all groups
are packed into a single backing storage via vLLM's existing `_get_packed_kv_cache_layout`
(`offset/block_stride`). The Mamba reshape and startup memory accounting are updated for packed
views; the scheduler, block pool, and coordinator are unchanged. The runtime MVEx passes 8/8
checks (single backing storage per worker, mixed INT4/NONE attention quantization, GDN temporal
state fp32, correct non-empty generation).
