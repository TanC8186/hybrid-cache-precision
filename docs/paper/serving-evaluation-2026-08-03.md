## 1. Experiment Setup

**Platform.** All serving experiments run on a single RTX 5090 (32 GB HBM, Blackwell sm_120)
in the pinned Docker environment of `configs/env/remote_5090.yaml`. We use **Qwen3.5-2B**, a
hybrid linear-attention transformer with 18 Gated DeltaNet (GDN) layers and 6 standard GQA
attention layers at indices $\{3,7,11,15,19,23\}$, each attention layer with 2 KV heads of
head_dim 256. The serving stack is a vLLM **0.26.1rc1** fork (`vendor/vllm`) carrying two
patches: per-layer `kv_cache_dtype` override and a CLI-help fix (diff archived in
`vendor/vllm-patches/`). Servers run as OpenAI-compatible endpoints (`vllm serve`); load is
generated by `vllm bench serve`.

**Configurations compared.** (a) **fp16 baseline**: `kv_cache_dtype=auto` (bf16). (b) **int4
per-layer (ours)**: `kv_cache_dtype=int4_per_token_head` with `kv_cache_dtype_per_layer`
overriding layer 23 to `float16` and layers $\{3,7,11,15,19\}$ to int4-per-token-per-head. The
layer-23 protection is motivated by the sensitivity analysis of §6, where layer 23 is the most
quantization-sensitive attention layer.

**Protocol.** Both servers use `gpu_memory_utilization=0.85`, `max_model_len=4096`,
**CUDA-graph mode** (`enforce_eager=False`), and `enable_chunked_prefill=True`. The benchmark
(`vllm bench serve --dataset-name random`) issues **400 requests per rate point** with fixed
**input_len=1024 / output_len=128** (confirmed in server logs), Poisson arrivals
(`burstiness=1`), `--max-concurrency 512`, and offered rates
$R \in \{1,4,8,12,16,20,30,40,50,75\}$ req/s. All points complete with **zero failed
requests**. `num_warmups=0`; server-side `disable_log_stats=False` so `RequestOutput.metrics`
(TTFT/TPOT) are recorded.

**SLO.** Following `configs/bench/throughput.yaml`, an allocation is SLO-compliant when
**TTFT p99 < 2000 ms and TPOT p99 < 200 ms**.

## 2. E1 — KV Cache Capacity

Under a fixed GPU memory budget, int4-per-layer grows the KV cache from 1,203,106 to
2,701,721 tokens and the engine's maximum concurrency from 293.7 to 659.6 sequences
(Table 1; server startup logs archived in commit `525020f`). The end-to-end capacity ratio is

$$\text{capacity} = \frac{2,\!701,\!721}{1,\!203,\!106} = 2.2456\times .$$

| allocation | KV cache (tokens) | max concurrency | KV cache memory |
|---|---|---|---|
| fp16 | 1,203,106 | 293.7 | 20.12 GiB |
| int4 per-layer (ours) | 2,701,721 | 659.6 | 20.08 GiB |
| **ratio** | **2.2456x** | **2.245x** | — |

**Table 1.** E1 capacity from server startup logs (`GPU KV cache size` / `Maximum
concurrency`), Qwen3.5-2B, gpu_util=0.85, max-len 4096, CUDA-graph mode.

**Dual caliber.** The *mechanism-level* compression of the attention KV cache alone is
**3.88x**: each GQA layer stores $2 \times 256 \times 2\,\text{B} \times 2\,(K{+}V) =
2048\,\text{B}$ per token per layer in fp16, and ${\approx}528\,\text{B}$ under
int4-per-token-per-head (including the per-token scale), so $2048/528 = 3.878x$. This matches
the offline slot counts (7,434,528 int4 vs 1,917,056 fp16, §5/§6). The *system-level* ratio is
**2.2456x** — i.e. **only ~58% of the mechanism-level gain survives** end to end.

**Why: non-quantizable Gated DeltaNet state.** The GDN recurrent state is stored per sequence
and is *not* quantized by the KV scheme. From `MambaStateShapeCalculator
.gated_delta_net_state_shape` (`vendor/vllm/.../mamba/mamba_utils.py`):

- temporal state `(num_v_heads=16, head_v_dim=128, head_k_dim=128)` = 262,144 elements, fp32
  → 1,048,576 B;
- conv state `(conv_dim=6144, conv_kernel-1=3)` = 18,432 elements, bf16 → 36,864 B;
- per layer **1,085,440 B**; × 18 layers = 19,537,920 B ≈ **18.63 MiB per request**.

GDN state grows **linearly with the number of concurrent sequences** (independent of context
length) and is drawn from the *same* KV-cache memory pool as the attention blocks. At the int4
server's maximum concurrency (659.6 sequences), aggregate GDN state ≈ 12.0 GiB ≈ **60% of the
20.08 GiB KV-cache budget** **[VERIFY — provenance estimate, see §7]**; at the 400 requests
observed in flight at the highest offered rate it is ≈ 36%. Because this fixed per-sequence cost
is identical for both allocations, it dilutes the 3.88x attention-KV gain to 2.2456x end to end.

**Structural implication.** In a hybrid architecture, quantizing only the (small number of) GQA
attention layers has a capacity ceiling set by the linear-attention per-request state. Further
capacity gains require either compressing the GDN state itself or an honest end-to-end caliber.
**We report both calibers** (mechanism 3.88x, system 2.2456x) throughout.

**Results.**

1. **Saturation goodput.** At the highest offered rate (75 req/s — fully saturated: all 400
   requests in flight), int4-per-layer sustains **38.14 req/s / 4,882 out-tok/s** vs fp16
   **36.26 req/s / 4,641 out-tok/s** (+5.2%). The plateau is stable across $R=50 \to 75$
   (int4 37.46 → 38.14; fp16 35.72 → 36.26).
2. **Capacity converts into load-bearing.** The 2.245x larger cache (659 vs 294 max
   concurrency, §2) lets int4 absorb offered load with less queue buildup: at $R=50$ int4 is
   already saturated (37.46 req/s) while fp16 sits at 35.72; at $R=75$ int4 goodput still
   rises while fp16 plateaus.
3. **Low-load overhead (honest).** At $R=1$ fp16 has lower latency: TTFT p99 115.9 vs
   124.8 ms (**+7.7%**) and TPOT p50 3.52 vs 3.80 ms (**+8.0%**). This is the per-step
   lazy-dequantization cost, consistent with the offline TPOT p50 +8–10% (§5), and is visible
   whenever the GPU is not saturated.
4. **High-load reversal (single-run).** At $R \ge 50$, int4 TPOT p50 is slightly *below* fp16
   (R=75: 40.97 vs 42.86 ms), plausibly because the larger cache reduces queueing/preemption.
   Single-run observation; direction only.

## 4. E3 — SLO-Constrained Capacity

Figure 2 (`fig2_slo_ttft.png`) plots TTFT p99 vs. offered rate for both allocations with the
SLO bound (2000 ms) as a horizontal line. Table 3 summarizes the SLO reading.

| allocation | max SLO-compliant rate | TTFT p99 @ max rate | first violating rate (TTFT p99) |
|---|---|---|---|
| fp16 | **40 req/s** | 566.3 ms | 50 (2081.3 ms) |
| int4 per-layer | **50 req/s** | 1574.1 ms | 75 (4036.7 ms) |

**Table 3.** E3 SLO analysis under the `configs/bench/throughput.yaml` SLO (TTFT p99 < 2000 ms
and TPOT p99 < 200 ms).

**Result.** int4-per-layer carries **+25% offered load** (50 vs 40 req/s) while meeting the same
SLO. The SLO-violation cliff is pushed out by one rate tier and with more headroom: fp16 first
violates at 1.04x the bound (2081 ms), int4 at 2.02x (4037 ms).

**TPOT is not binding anywhere.** Across all 20 points, TPOT p99 stays ≤ 49.3 ms (max at fp16
R=75), far below the 200 ms SLO bound; the SLO is **TTFT-bound** in both allocations.

## 5. TPOT Per-Token Cost

Figure 3 (`fig3_tpot.png`) plots TPOT p50/p99 vs. goodput for both allocations (4 lines).

**Real per-step cost.** The honest cost of int4 KV quantization is a per-token latency increase
from per-layer RHT dequantization and the Triton attention kernel. Offline 3-seed measurements
(@4096, warmup protocol, `enforce_eager=True` — note this differs from the CUDA-graph serving
protocol) give **TPOT p50 +8.6%** for int4-per-layer (34.0 vs 31.3 ms) and **+10.9%** for
uniform int4 (34.8 vs 31.3 ms), with throughput −6.4% (−5.0…−8.1% across seeds) and −8.4%
respectively. At 8192 context (single seed) the throughput cost shrinks to −2.3% / −3.1%. These
directionally match the low-load latency gap in §3.

**p99 tail is not an inherent int4 cost.** We initially observed a large TPOT p99 tail for int4
in a non-warmed serving run (p50 31→44 ms, **p99 894 ms**, ratio ≈ 20x). Root-cause analysis
(`jit_monitor` logs + backend selection) shows the spike is a **serving-time Triton JIT cold
compile** of the int4 attention kernels (`_attn_packed`, `reduce_segments`): int4 forces the
`TRITON_ATTN` backend (fp16 uses the precompiled `FLASH_ATTN`), and the engine profile/warmup
paths do not pre-compile the 2D-decode specialization (decodes with batch > 64), which is first
compiled inside the measured window. Re-running with `--warmup-n 120` (warmup concurrency
120 > 64, forcing all decode specializations) **eliminates the spike**: int4-per-layer TPOT p99
returns to ≈ 124.7 ms (3-seed mean), comparable to fp16 (145.5 ms) and actually lower, though
with high variance (28.6% rel. std). In the CUDA-graph serving matrix (§4) TPOT p99 stays
≤ 49.3 ms throughout. **We report warmup-clean TPOT and disclose the warmup gap in §7.**

## 6. Quality under a Byte Budget

The serving gains rest on int4 quality. Table 4 reports per-token quantized-KV PPL on
Wikitext-2 (5 × 2048-token sequences, greedy, deterministic) across bit-widths and eviction
retention, plus the sensitivity-guided per-layer allocation (§1).

| bits | keep (tokens) | KV bytes | PPL | vs FP16 |
|---|---|---|---|---|
| 2 | 2048 (full) | 3,366,816 | 21.07 | +55% |
| 3 | 2048 (full) | 4,852,176 | 15.87 | +16% |
| **4** | **2048 (full)** | 6,436,560 | **13.86** | **+1.7%** |
| 8 | 2048 (full) | 12,774,096 | 13.63 | ≈0 (lossless) |
| FP16 | — | 25,350,144 | 13.63 | baseline |
| 4 | 1024 | 3,194,880 | **14.10** | — |
| 2 | 2048 (full) | 3,366,816 | **21.07** | — |
| 4 | 1536 | 4,792,320 | 13.89 | — |
| 3 | 2048 (full) | 4,852,176 | 15.87 | — |

**Table 4.** Quality (Wikitext-2 PPL) from `results/ablations/byte_budget_ordering.csv`.
Bottom four rows are equal-byte-budget comparisons.

**Findings.**

1. **8-bit is lossless** (13.63 = FP16 baseline); **4-bit is near-lossless** (13.86, **+1.7%**);
   3-bit +16% (15.87); 2-bit +55% (21.07). The sub-4-bit region is the tension zone.
2. **Equal-byte-budget ordering: high precision + eviction beats low precision + full
   retention.** At ≈ 3.2 MB, 4-bit with keep-1024 eviction scores **PPL 14.10 vs 2-bit full
   retention 21.07**; at ≈ 4.8 MB, 4-bit keep-1536 (13.89) beats 3-bit full retention (15.87).
   Under a fixed byte budget, *evict tokens before dropping below 4-bit*.
3. **Layer heterogeneity.** The 6 GQA layers are highly heterogeneous: forcing layer 23 to 2-bit
   costs +28.7% of the 2-bit sensitivity range (PPL 15.76 vs 13.63) — the most sensitive layer —
   while layer 3 is essentially free (−5.9%). This motivates the per-layer budget used in §2–4
   (layer 23 protected in fp16, all other GQA layers int4).
4. **Sensitivity-guided allocation beats uniform at equal bytes.** `sens_guided`
   {3:2bit, middle 3bit, 23:4bit} → **PPL 14.63 @ 4.87 MB** vs uniform 3-bit 15.87 @ 4.85 MB;
   `only_layer3_2bit` {3:2bit, others 4bit} → PPL 13.39 @ 5.92 MB — better quality *and* fewer
   bytes than uniform 4-bit (13.86 @ 6.44 MB).

## 7. Discussion / Honesty

We state the caveats that qualify every claim above.

- **Model scale.** All serving results use **Qwen3.5-2B**. The headline claims (2.245x
  capacity, +25% SLO load, ~+5% saturation goodput) must be re-validated on a **7B** model in
  the `remote_5090` environment before final submission.
- **Workload.** The E2/E3 matrix uses a synthetic `random` workload with fixed 1024-token
  inputs / 128-token outputs; it is **not a real trace** (ShareGPT). Variable-length and
  real-traffic request mixes may shift the SLO boundaries.
- **Statistics.** The E2/E3 matrix is a **single run per (allocation, rate)** — no 3-seed
  mean±std. Cross-point comparisons carry scheduler noise; the low-load int4 deficit (§3.3) and
  the high-load TPOT reversal (§3.4) are single-run observations — direction credible, precise
  values pending replication. The offline quality/throughput numbers (§5–6) do carry 3-seed
  mean±std where stated.
- **Protocol.** The E2/E3 matrix uses `num_warmups=0`; the offline matrix mixes `warmup_n=5`
  and `warmup_n=120` across allocations, and the JSONs did not record `warmup_n` (provenance
  gap, R1 fix). §5 shows the warmup protocol can dominate p99 conclusions.
- **Capacity provenance.** Server startup logs (KV cache size, max concurrency) are archived in
  commit `525020f`. The **GDN ≈ 60%-of-budget** figure is derived from the archived max
  concurrency and the code-derived per-sequence state size; it is an estimate and should be
  re-verified against the exact logged KV-memory split **[VERIFY]**.
- **Both capacity calibers are reported** (mechanism 3.88x, system 2.2456x) to avoid
  overselling the compression ratio.
